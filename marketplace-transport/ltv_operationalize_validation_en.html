① Decision chain (what validation must support)

One flow, not four separate models.

  1. Tier (value band) — is this customer worth spending on? (P100–P10 or list T1–T5)
  2. BG/NBD + Gamma-Gamma — inside the same Tier, who first, and how hard?
  3. Recency group — act now? ≤90 / 91–180 / >180 days since last completed job
  4. Marketing / CRM action — service, push, offer, or no spend
  5. Validation — prove each Tier × Recency cell is reliable in hard windows

Core line from spec: Tier decides worth; BG/NBD+GG decides who and how hard; Recency decides now or later; Validation proves it is safe to use.

② Accuracy vs Projection

A zone · Accuracy Validation

Windows with real orders: 30 / 90 / 180 days (and existing main_90d / sens_180d).

Compare forecast to Actual. Report Bias, calibration ratio, Pass / Fail.

This is the only place we may say “accurate enough for ops”.

B zone · Projection Validation

Beyond holdout out to 120 months.

Check path shape, decline assumption (~15%/year), scenario bands.

Never say “10-year error is X%”. There is no 10-year answer.

Forbidden claim: “Future 120 months is accurate within X%.” Allowed claim (after A-zone Pass): well calibrated on the observable horizon; path consistent with an independent BG/NBD + Gamma-Gamma forecast.

How the two formulas work
  • Predicted LTV = BG/NBD (how many more customer order days) × Gamma-Gamma (platform_take per order day). More flexible on history window: can use about 90 days, 1 year, or the full ranking span (~821 days) to build frequency / recency / T, then forecast forward 91 days (or longer).
  • Estimated LTV = ranking Year 1 × (91 ÷ 365) for this short test. Year 1 = calib_platform_take × 365 ÷ GREATEST(T, 91) — only money up to the cut-off. Less flexible on behaviour (no per-customer recency rhythm), but Year 1 can still be defined from ~90d / 1y / full ranking money. Yearly decay (P100 3.0%/yr · P99 18.1%/yr · P90 30.1%/yr) turns Year 1 into the 10-year Estimated LTV on the homepage (Year1 × lifetime_mult_10y) — not copied from holdout.
What MAE means (easy example · P100 Predicted)
  • MAE HK$322.7 = for each customer, take |Predicted $ − Actual $|, then average. That is the average miss per customer. Lower is better. Always ≥ 0 (no plus/minus — only “how far off”).
  • |595.8 − 682.9| = HK$87.1 = difference of the two averages (group bias). This matches the +/− % deviation (-12.8%), not MAE.
  • Why they differ: some customers are over-predicted, some under. Over and under partly cancel in the averages → only about 87 left. MAE takes absolute miss first, so misses do not cancel → 323. So -12.8% ↔ the 87 bias; 323 = average dollars wrong per customer.

Bias = (predicted sum − actual sum) / actual sum. Calibration ratio = predicted sum / actual sum. Actual is the only truth.

Pass rule (spec): at least LTV vs Actual must pass for that Tier × Recency cell. BG vs Actual strengthens confidence. Model Gap small while both miss Actual → Fail.

⑤ Triangulation (how we will judge)

Two independent forecasts, both checked against Actual. Models agreeing with each other is not enough.

  • LTV vs Actual → Bias / WAPE (accuracy)
  • BG/NBD+GG vs Actual → Bias / WAPE (accuracy)
  • LTV vs BG/NBD+GG → Model Gap only (consistency, not accuracy)
Why model-vs-model is not enough: LTV = $100, BG = $101, Actual = $60 — the two models agree and both are wrong. Actual stays in the centre.

Independence rule: LTV Model must not be the same number as BG×GG CLV (e.g. not lifetimes.customer_lifetime_value() as the LTV arm). Else drop that arm.

Still missing for layer 2: per-customer still_active_probability / P(alive) and 90-day return probability are specified but not in BQ yet (method step 3). Until then, do not label recency_over_T as “still active probability”. recency_over_T is a model input, not P(alive). Temporary proxy for targeting: high past calib_platform_take + mid recency ÷ T (about 0.4–0.7).
